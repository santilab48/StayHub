## Fix for the Production migration hook

The previously deployed migration hook hardcodes `current_database()='railway'`. A naive Neon `DATABASE_URL` switch would cause the Production pre-deploy step to fail because Neon uses `neondb`. The feature-branch fix leaves the existing Railway path unchanged. A future Neon switch requires **both** `STAYHUB_DB_PROVIDER=neon-production` and `STAYHUB_NEON_PRODUCTION_HOST` equal to the verified Neon Production endpoint hostname; the app and migration preflight reject wrong project/environment/host/database. The connection enforces `sslmode=verify-full`; the preflight verifies the live TLS socket and `neondb_owner`. On Neon, it checks that every migration filename/checksum is already present, rejects missing/extra history and **does not apply migrations**. The staging route remains available; Production transport returns 404 until that explicit provider is active. The Production source branch does not include this feature-branch fix yet, so a code promotion is a separate approval gate.

The endpoint hostname must be obtained from the Neon Production branch in the owner's secure console and compared to the intended connection URL. Never put a password or full URL in a commit, log, issue or this document. The hostname alone is insufficient proof of branch identity; recheck project/branch/database and read-only migration/count results during the cutover window.

3. Capture a recoverable, timestamped backup of the actual Railway PostgreSQL database, including schema, extensions and data. Verify a restore to an isolated disposable PostgreSQL target and compare 20 table counts, 11 checksums, indexes/constraints and billing totals. Keep the old service/volume intact. Confirm retention, access and recovery time with the owner; an untested backup is not a rollback proof.
4. Save the original Railway app `DATABASE_URL` **reference/value in an approved secret store** with restricted access; verify an operator can restore it without displaying it in logs. 5. With explicit owner approval only, promote the reviewed code to Production **while the old Railway database remains selected**; verify its pre-deploy migration check and health. Then stage the Neon Production URL, `STAYHUB_DB_PROVIDER=neon-production`, and `STAYHUB_NEON_PRODUCTION_HOST` as one controlled change. Recheck the staged diff and intended endpoint. Freeze both sides; capture both databases' backups and read-only row/billing ledgers, reconcile accounts, stays, bills, payments, idempotency keys and timestamps, choose a single authoritative history with the owner, rehearse transfer and verify totals before redirecting. A blind rollback would hide or lose new writes and could duplicate payments.
