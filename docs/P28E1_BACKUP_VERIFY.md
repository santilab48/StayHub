## Windows PowerShell runbook, one verified step at a time

Use the already configured Railway CLI SSH tunnel. Keep its terminal open. The following commands are **prepared, not executed by this agent**. Work from the checked-out repository. Do not paste a connection string or password into chat. If the tunnel presents a different local host/port, use its actual local endpoint. `-W` lets PostgreSQL prompt locally for the password. Stop on any unexpected database identity, nonzero count, missing migration or failed command.

1. **Identity first:** set `$ProdPort = [int](Read-Host 'Existing Railway Production tunnel local port')`, then run `psql -h 127.0.0.1 -p $ProdPort -U postgres -d railway -W -X -v ON_ERROR_STOP=1 -c "SELECT current_database(), current_user, inet_server_addr(), current_setting('transaction_read_only')"`. Confirm `railway`/`postgres` and the intended tunnel. Do not substitute a staging, Neon or PAIR-LIVE endpoint.
2. **Exact inventory:** run `psql -h 127.0.0.1 -p $ProdPort -U postgres -d railway -W -X -v ON_ERROR_STOP=1 -q -t -A -f .\scripts\p28e1-readonly-fingerprint.sql`. Confirm the output has 20 `table|...` lines, all 19 business counts exactly zero **if relying on the empty-database plan**, 11 `migration|...` lines matching the repository hashes, and the expected catalog fingerprints. Keep a timestamped local copy of the metadata output. The database remains writable after this read-only query; no write freeze is implied.
3. **Backup:** verify `pg_dump --version` and `pg_restore --version` are 18.x. Choose a private local directory and filename that is not in the repository. Example: `$BackupFile = Join-Path $env:USERPROFILE ('StayHubBackups\stayhub-railway-' + (Get-Date -Format 'yyyyMMdd-HHmmss') + '.dump')`; create its parent directory locally. Run `pg_dump -h 127.0.0.1 -p $ProdPort -U postgres -d railway -W -Fc --no-owner --no-acl -f $BackupFile`. Check `$LASTEXITCODE -eq 0`, nonzero `(Get-Item $BackupFile).Length`, `pg_restore --list $BackupFile` succeeds, and record `Get-FileHash -Algorithm SHA256 $BackupFile`. The dump can contain actual user data; restrict file access and retention. A successful dump/list alone is not a proven restore.
4. **Separate restore target:** identify an existing authorized PostgreSQL 18 test database with its own host/port and credentials. Verify its identity using `psql` and that it has **no `stayhub` schema**. Require an explicit test database name other than `railway` and `neondb`; do not use the Production tunnel or Neon Staging/Production. If no verified empty target exists, stop: restore stays **BLOCKED**.
5. **Restore and compare:** only after step 4, run `pg_restore -h <test-host> -p <test-port> -U <test-user> -d <verified-empty-test-db> -W --single-transaction --exit-on-error --no-owner --no-acl $BackupFile`. Check exit code zero. Run the same fingerprint SQL with `psql` against that test database. Compare the sorted `table|`, `migration|`, `catalog|` and `extension|` lines from source and restore with PowerShell `Compare-Object`; an empty difference plus matching SHA-256 and successful health/row checks is the restore evidence. Database identity lines differ by design and are excluded from comparison. Never add `--clean`, `--create` or restore into an existing business schema.

The tunnel command itself is not repeated because the user's tunnel is already configured; the local forwarded port must be read from that active session. Before changing Production in a later approved window, repeat the exact counts **under an actual enforced write freeze**, verify the real backup's restore and record a secure, tested path for reverting the original `DATABASE_URL`. Any new Railway business row makes the empty-database cutover plan **NO-GO**. No Production deployment, variable switch, merge, database deletion or Neon write occurred here.
