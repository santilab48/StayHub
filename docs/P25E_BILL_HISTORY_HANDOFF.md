## Backend API

- `GET /api/v2/bills`: property scoped owner/admin history or authenticated tenant's own historical bills. Optional `propertyId`, `period=YYYY-MM`, `unitId`, `status=unpaid|partial|paid|void`, `page` (1–200), `limit` (1–50, default 25). With a property ID and owner/admin membership, show all bills of that property. Without membership, scope to the session account's bills; omitting property ID allows a tenant to see their own bills across properties. The response returns `items`, `page`, `limit`, `hasMore`; the query fetches one extra row to determine `hasMore`. Items include original `stay_id`, `account_id`, unit name, total, confirmed paid and outstanding. Stable order is period, created time and bill ID descending.
- `GET /api/v2/bills/[billId]?propertyId=...`: one finalized bill, snapshotted rent/water/electric/other items, total and paid/outstanding. Owner/admin gets up to 50 payment records and `hasMorePayments`; a tenant receives no internal receipt history or confirmer IDs. Authorization is by session account against the **stored bill account** or property membership, not a currently active Stay or a room number. Read-only repeatable-read transaction keeps detail and sum consistent.
- `GET /api/v2/bills/summary?propertyId=...` with the same period/unit/status filters: owner/admin only, count of matching bills, billed total, confirmed paid total, outstanding total and unpaid/partial count. Voided bills remain countable when selected but are excluded from monetary totals and outstanding. There is no accounting/profit calculation.
- `GET /api/v2/bills/[billId]/payments?propertyId=...&page=...`: owner receipt history now paginates at 50 per page. Tenant still receives only status, total, paid and outstanding. `POST` remains owner/admin only with the existing idempotent, locked payment logic.

`lib/db/billing-history.ts` centralizes strict filter parsing and the parameterized property/account scope for list and summary. Queries always require `finalized=true`; no client-supplied account ID is accepted. A historical bill retains its `stay_id`, `account_id`, `unit_id` and `lease_id` even if the resident moves or checks out, so a later occupant of the same unit cannot see it. All URLs return `Cache-Control: no-store`; there are no UI changes or new tables/migrations.

## UI reuse assessment

`components/AdminBillBuilder.tsx` and `components/MeterEntryWorkspace.tsx` still read/write browser Supabase `invoices`, `invoice_items`, `meter_readings`, legacy `rooms` and `leases`. They cannot safely be repointed by a simple URL swap because the new API uses server session + UUID identity binding and immutable issued snapshots. Existing tenant billing entry is likewise not proof that the PostgreSQL history is displayed. Later UI work may reuse labels and layout, but must replace the data source and remove the legacy invoice upsert/delete-reinsert pattern. Existing local-first storage remains separate; shared bill history is server-authorized PostgreSQL data.
