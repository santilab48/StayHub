# StayHub tenant PWA installation and device approval

Date: 24 November 2026 (Asia/Bangkok). Repository `santilab48/StayHub`, branch `feat/stayhub-p26-readiness`. Base remote HEAD: `7ff30f1afece2fde3960adaf89320c368c787c6b`.

## Implemented

- A room QR still uses the existing owner create-QR action. Its `/join?token=...` page initially contains the StayHub logo and install action or Android/iPhone add-to-home instructions. It does **not** contain email/password, account signup, login, room activation or other form before installation.
- The QR page serves a per-invitation manifest **in the initial server HTML**. Its installed `start_url` retains the QR token so a new Android/iOS standalone storage context can open the same invitation without relying on shared LocalStorage. The actual QR URL is generated by the owner API; it is not hard-coded or published in this report.
- Standalone launch shows one room-number field and a confirm action. Backend checks the QR hash, expiry, revocation, property and exact active room name. It creates a random device token, stores only its SHA-256 hash in PostgreSQL, sets a Secure HttpOnly SameSite cookie in deployed HTTPS environments, and creates a pending join request using an internal passwordless account. The user never enters an email/password.
- Device sessions cannot read private APIs while pending/rejected. After the existing owner approve action creates a matching active Stay, session lookup requires that Stay, exact property/unit/account/request match, unexpired token and no revocation. The existing owner request list shows the room and an anonymized device label, supports approve/reject and adds device revocation. Reopening an approved installed app goes directly to `/my`; revocation or checkout removes private access.
- Migration `018_tenant_devices.sql` adds the scoped device/token table and FK to the existing join request. No room-management system was duplicated. Existing bill/PDF generation was not changed.

A separate 360 px standalone context with no shared browser storage entered only the room number, observed pending state, and received owner approval through the existing owner screen. Closing and reopening with its session entered the dashboard without a second room entry. The owner screen revoked the device and the private API denied access.
- Existing isolated Auth/QR/Billing HTTP regression passed. TypeScript and Build passed. No fixture from this test touched Staging or Production.

## Staging and physical-device limits

- This environment has no Railway/Neon management connector or Staging database credentials. HTTPS request to the Staging health endpoint was rejected by the outbound proxy with `CONNECT tunnel failed, response 403`; this does **not** establish that Staging is unhealthy. Migration 018, Staging deployment, logs and Staging PostgreSQL rows were **not** verified here. PWA/device flow must not be called live until migration and deployment have been confirmed against the correct Staging identity.
- The install-button event and standalone context were simulated in real Chromium; actual Android and iOS home-screen installation, OS storage boundaries and launch from a physical icon have **not** been tested on devices. The dynamic manifest URL is designed to survive separate storage, but physical-device acceptance remains open.
- The existing dashboard links to bills, announcements, parcels and repairs; the isolated HTTP test verified each API after approval. An owner must create a verified lease and bill for that device account before its tenant can see an invoice. Existing owner-only room-contract bills are not retroactively assigned to a device.
