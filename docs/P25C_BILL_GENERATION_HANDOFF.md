## Files and behavior

- `db/migrations/011_bill_issue_idempotency.sql`: optional issue key and SHA-256 request hash on P2.5-B bills, unique within property, immutable once stored. Migration 010 remains intact. Use the existing migration runner only against a separately authorized target later; this work did not execute any migration.
- `lib/db/billing-calculation.ts`: decimal parsers use integer thousandths for consumption and integer cents for money; water/electric amount rounds once to two decimals. The first meter reading requires an explicit baseline. Decreasing readings and values beyond schema range are rejected.
- `lib/db/billing-request.ts`: UUID, month, safe idempotency header and owner/admin membership helpers.
- `app/api/v2/meter-readings/route.ts`: authenticated owner/admin POST. Locks the property/unit, fetches the last earlier same-type reading for the same unit, accepts explicit initial baseline only when no prior reading exists, rejects older gaps after a newer reading, duplicates, decreases and overflow. No edit endpoint; migration 010 blocks updates to readings used on bills. Water and electricity are separate.
- `app/api/v2/bills/route.ts`: authenticated owner/admin POST issues one monthly bill for an existing active lease, verified Stay and property. The physical unit is locked, tenant/unit/stay are derived server-side, the lease and billing period are validated, and all reading/item amounts are snapshotted in one transaction. Prevents duplicate lease/month, duplicate meter allocation, ambiguous occupancy from transfers/shared rooms, and replay of an idempotency key with changed request. Rent comes from the lease; optional other charge is explicit. Missing meter readings simply add no utility item. GET lists finalized property bills for owner/admin, or only the signed-in tenant's own historical bills; no direct browser database access.
- `scripts/test-bill-generation.mjs`: deterministic decimal/meter scenarios plus structural checks for property/account/stay binding, duplicate guards and issue key.

The API requires `STAYHUB_ENABLE_TEST_SIGNUP` staging authentication gate, session and same-origin POST. `POST /api/v2/meter-readings` takes `propertyId`, `unitId`, `meterType`, `period` (`YYYY-MM`), `currentReading`, `unitRate` and `initialReading` only for the first reading; decimal values are strings. `POST /api/v2/bills` takes `propertyId`, `leaseId`, `period`, optional `otherAmount` and `otherLabel`, and a 16–128 character `Idempotency-Key`. The caller does not provide recipient, total, stay or unit for bill creation. Neither route is connected to existing legacy Supabase UI. No payment endpoint exists yet.
