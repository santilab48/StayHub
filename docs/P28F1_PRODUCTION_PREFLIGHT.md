## Required write-stop design and future cutover runbook (not executed)

1. **Pre-window identity and recovery:** inventory every Production writer and credential holder, including external clients, app deployments, admin tunnel, CI/job tokens and migration hook. Verify the app uses a **dedicated, non-superuser database role distinct from the recovery/admin role**. If it shares an admin credential or external writers cannot be excluded, **NO-GO**. Securely escrow and test retrieval of the exact original Railway `DATABASE_URL` reference/value without logging it. Confirm the operator can restore the existing provider setting. The current connector cannot perform these proofs.
2. **Rehearse the barrier on Staging or an isolated PostgreSQL target:** establish an ingress maintenance response for every app domain/API path before altering deployment; hold new traffic, account for direct origin access. Stop scheduled or external writers. Record request and connection baselines. Drain in-flight requests and old rolling-deployment instances; ensure old versions cannot accept traffic. Use a dedicated app role and an independently managed admin connection to block **new app-role sessions and writes**, then terminate/verify remaining app-role backends only after the drain. Do not apply `NOLOGIN`, revoke privileges or terminate sessions on the current Production source in F1. A role's default `transaction_read_only`, one read-only `psql` session, or the app middleware alone is insufficient. Rehearse re-enabling the app role and thaw without dropping schema or losing data. If the platform cannot provide a verifiable ingress barrier and isolated DB-role barrier, redesign before cutover.
3. **Approved Production window, promote code separately:** only after explicit owner authorization, promote the feature code **while still using the old Railway provider** and check its pre-deploy migration history/health. Any DDL or source mismatch stops the operation. A code promotion itself is a Production deployment, forbidden in F1. Pause further automatic deployments before maintenance. Confirm the actual deployed commit and all replicas; do not confuse a Git push to this feature branch with Production promotion.
4. **Enter maintenance and drain:** apply the rehearsed ingress gate first; verify 503 for writes and session-capable routes and 200 for approved health. Wait for in-flight traffic and old deployments to drain with observability; block other client credentials and stop jobs. Verify role/session inventory with `scripts/p28f1-writer-audit.sql` via the already authenticated Railway source tunnel, then enforce and verify the tested DB writer barrier. Unexpected sessions, inaccessible role identity, old instances or continuously changing counters are **NO-GO**. Keep a separate privileged, read-only audit connection available. Do not confuse an idle connection with permission to resume writing.
5. **Fresh source and target fingerprint:** under the proven barrier, run `scripts/p28e1-readonly-fingerprint.sql` on the **existing Railway Production** source from a verified connection, compare exact 19 business counts and 11 checksums. Repeat after a wait interval to detect changes; any nonzero/changing business count stops the **empty-database** cutover. On Neon Production, separately recheck project/branch/role, 20 tables, 11 exact checksums and 19 zero business counts using read-only SQL. A snapshot alone is not the barrier.
6. **Backup gate:** take a new timestamped `pg_dump -Fc` from the frozen Railway source; check exit/size/hash/archive list. Restore it to a separately identified empty PostgreSQL 18 test database, verify all 20 table counts, 11 migrations/checksums and catalog fingerprint against the frozen source. Do not overwrite the prior operator dump. If the real source backup cannot be retrieved and restored, **NO-GO**.
7. **Controlled Neon switch:** with maintenance and writer barrier still effective, use the separately escrowed `STAYHUB_NEON_PRODUCTION_URL`, verified host and `STAYHUB_DB_PROVIDER=neon-production` as an explicitly authorized controlled Production change. Keep `DATABASE_URL` exactly as the Railway rollback reference. Check pre-deploy logs for checksum-only Neon history validation (no migration application), TLS certificate, Production endpoint/role/database identity, `/api/health/db` and `/api/health/db/transport`; only then consider guarded Auth/Billing smoke. A Production app→Neon connection has **not** been proven in F1.
8. **Rollback and controlled thaw:** if no Neon write occurred, keep maintenance, reselect the original Railway provider/reference, verify old DB identity/health/counts, then remove the DB/ingress barriers in the rehearsed order and monitor. If **any** Neon write occurred, keep both sides frozen, back up and reconcile accounts, stays, bills, payments and idempotency keys before selecting one authoritative timeline; never blindly repoint and hide payments. Thaw only after explicit go/no-go sign-off and monitoring of errors, counts and transaction activity.
